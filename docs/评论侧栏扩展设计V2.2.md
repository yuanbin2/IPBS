# Blog V2.2 评论侧栏扩展设计

> 2026-10-02。B-038 的兼容分页接口与前端按需读取已在本地实现；真实 PostgreSQL 性能和读者任务仍待验收。关联缺陷：B-038。已登录且未受限制的读者可对同一工作空间的已发布文章直接发表评论；匿名可读但不能发言。

## 目标与现状

阅读长文时，侧栏应先帮助读者找到与当前位置有关的讨论，再允许浏览全部评论。即使一篇文章有数千条评论，打开文章也不应下载、渲染或计算所有评论的高亮位置。

旧客户端请求详情时，`BlogArticleSerializer.get_comments()` 仍返回全部已公开评论。新前端的详情请求带 `include_comments=0`，由独立接口读取普通评论与划线评论；侧栏/文末每批最多 20 条。私人高亮/旁注仍单独每页 50 条，不与公开评论共享分页状态。

## 产品交互

1. 已发布文章始终保留可折叠的“划线讨论”入口，匿名读者也能打开；展开后才加载第一页并取得总数，没有评论时显示空状态。登录读者另可查看自己的私人高亮/旁注。侧栏区分“当前选段”和“全部划线评论”；当前没有选中文字时，默认显示最近的公开划线评论。普通评论仍放在文章末尾，避免把两种讨论混在同一列表。
2. 侧栏和文末评论各显示最新 20 条，顶部同时显示准确总数与当前批次，例如“20 / 137”。按钮“更早评论”“较新评论”切换批次；页面一次只保留当前批次的评论卡片。每条摘录默认收起为两行，点开后显示全文。阅读正文的滚动位置不因翻评论而变化。
3. 点击已加载的划线评论，继续按现有 `quote + anchor_offset` 定位原文；定位失败时显示“原文可能已修改”，仍可阅读评论，不自动跳到错误位置。点击正文中的高亮时，只展示**当前已加载**的匹配评论，不暗示这是该段的全部讨论。
4. 新评论成功后回到最新一批并立即显示；管理员隐藏或读者刷新后，列表与总数按服务端结果更新。折叠侧栏时移除卡片 DOM，保留当前批次游标以便重新打开。
5. 窄屏继续使用可折叠侧栏/抽屉，打开时不覆盖“举报”“更早评论”等操作；按钮、计数和引用均支持键盘与屏幕阅读器。

## API 与兼容顺序

| 阶段 | 改动 | 原因 |
| --- | --- | --- |
| A：新增分页读取 | 给现有 `GET /api/agent/blog/articles/{slug}/comments/` 增加可选 `kind=quote\|plain&limit=20&before_id=...`。带分页参数时返回 `{items, total, next_before_id}`，未带参数时暂保留旧数组响应。按 `id DESC` 稳定排序，`limit` 最大 50，游标必须是正整数。 | 不立即破坏旧客户端；按 `id` 游标在新评论插入时不会出现 offset 翻页的重复/跳页。两类评论分开请求和计数，侧栏不会被大量普通评论挤空。 |
| B：新前端切流 | 文章详情请求带 `include_comments=0`，详情序列化器跳过 `comments` 字段；已发布文章侧栏入口不再依赖 `article.comments.length` 才显示。侧栏展开时取划线评论第一页，文末评论进入视口时取普通评论第一页。详情保留现有 `comment_count`。 | 避免仅给新接口分页、详情却仍下载全量评论的假优化；匿名读者在尚未加载评论时也能发现讨论入口。普通评论不必在读者刚打开文章时就加载。 |
| C：旧契约退场 | 新前端和桌面壳验收后，观察仍在使用旧数组接口的客户端；另行版本化或宣布迁移窗口，再考虑把默认无参数请求改成分页。 | 不在同一次发布中静默截断旧客户端的数据。 |

分页查询与文章详情使用同一 workspace、已发布状态检查；匿名只能读公开评论，发表评论仍按 B-037 检查真实登录、账号限制与限流。`is_approved=False` 的历史待审或已隐藏评论不进入 `items` 和 `total`。对未知文章、私有草稿和其他工作空间继续返回 404。刷新后游标指向已隐藏评论也应正常返回下一批，不报错或泄露内容。

## 数据库与性能

优先用现有 `BlogComment.article_id` 外键与主键验证查询计划；若真实 PostgreSQL 在 1,000/10,000 条评论样本下不达标，再通过独立迁移增加 `(article_id, is_approved, id DESC)` 索引。`kind` 目前由 `quote` 是否为空过滤；只有查询计划证明必要时，才考虑部分索引。不要为了纯展示再引入搜索引擎或缓存整篇评论列表。分页计数必须来自数据库，不能从已加载的 20 条推算。

第一阶段不新增持久化“段落 ID”。现有 `quote + anchor_offset` 在文章修订后可能漂移；先对定位失败给清楚提示。若用户任务证明需要“某一段共有 N 条”的准确聚合，再单列锚点版本/上下文迁移与旧评论回填设计；不把当前批次的数量冒充全量段落计数。

## 小步实施与验收

1. **后端先行**：增加可选分页契约和 `include_comments=0`，保留旧响应。用 1,000 条混合普通/划线/隐藏/历史待审评论验证游标无重复遗漏、两类总数准确、匿名/跨空间/草稿权限和限流不变。记录 SQLite 功能结果；真实 PostgreSQL 查询计划与 P95 留作发布验收。
2. **前端切流**：侧栏和文末各维护自己的 `before_id` 栈与当前 20 条；只在需要时请求，显示加载中/失败重试/空状态。新发、举报隐藏、文章切换及连续点击翻页都要取消或丢弃过期响应。私人笔记分页状态保持独立。
3. **浏览器验收**：隔离 Edge 在 120 条混合评论下确认首屏公开评论卡片不超过 20 条/区域，翻页无重复，普通/划线分区正确；新发立即可见，隐藏后消失，旧待审不可见；折叠/窄屏/键盘操作正常。再运行博客后端类、前端构建和现有评论/标注 E2E。
4. **发布门槛**：真实 PostgreSQL 上以 1,000/10,000 条样本测文章详情与评论第一页的响应大小、查询数和 P95；目标是详情响应不随评论数增长，单次评论响应最多 20 条，侧栏与文末各最多渲染 20 张公开评论卡片，接口 P95 ≤300 ms。若数据库负载达不到目标，先看 `EXPLAIN` 再决定索引。实际移动设备和至少 5 名读者完成“找到指定评论、跳到原文、举报”任务，目标 4/5 在 2 分钟内完成。

## 回退

先保留无参数旧数组接口。前端可回退到旧读取方式，但大量评论性能风险会恢复；回退不删除评论或改变审核/举报状态。新增索引如有独立迁移，需在真实 PostgreSQL 验收后单独评估撤销，不与前端回退绑定。

## 本地实现记录

详情 `include_comments=0` 跳过评论序列化，仍提供准确的 `comment_count`；无参数评论 GET 继续返回旧数组。带 `kind`/`limit`/`before_id` 的 GET 校验输入、按公开状态与类型过滤，以 `id DESC` 返回当前批和数据库总数。前端匿名与登录读者均可展开划线讨论；普通评论进入文末视口时才加载，两个区域各维护独立游标和失败重试，切换文章或评论数变化会丢弃过期响应。划线高亮仅根据当前批计算，长摘录可展开。未改评论迁移或审核状态。

本地 1,000 条混合评论测试覆盖两类总数、逐批无重复遗漏、旧契约、匿名读取与无效参数；前端 `build:check` 通过。隔离 Edge 已验证匿名阅读、120 条模拟分页、新评论立即出现及管理员举报隐藏。模拟分页只验证浏览器状态和 DOM，真实 PostgreSQL 的查询计划/P95 与 5 人任务仍按发布门槛执行，B-038 保持待验收。
