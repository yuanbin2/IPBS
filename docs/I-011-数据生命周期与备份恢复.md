# I-011 数据生命周期与备份恢复（2026-10-23）

## 当前数据与删除边界

| 数据 | 存储与关联 | 当前删除/过期行为 | 恢复必需项 |
| --- | --- | --- | --- |
| 用户、文章、权限、笔记、文档、切片、运行记录 | PostgreSQL；本地模式 SQLite | 笔记是 `deleted_at` 软删除，未配置自动最终删除；其他对象按业务删除和外键级联 | 整库一致性快照、迁移版本、应用版本 |
| 文档原始文件 | `default` 文件存储；Compose `media_data` | 文档审批删除会删源文件；知识库级联删除不保证逐文件清理，可能留孤儿 | `media_data/knowledge/`；否则无法重新入库 |
| 公开博客图片 | `blog_media`，Compose 文件卷或独立 S3 Bucket | 审批删文章后复核共享引用再删；`prune_blog_media` 默认 dry-run、30 天宽限；真实 Bucket 尚未验证 | 文件卷中的 `blog/` 或 Bucket 的同一版本集合 |
| 私有笔记图片 | 独立 `private_note_media` 文件卷，按 owner/workspace 鉴权 | 未绑定图片超过 24 小时可预览；`cleanup_orphan_private_images(apply=True)` 才清理。软删除笔记仍保留附件；没有自动最终清除策略 | `private_note_data`；绝不可用公开媒体替代 |
| 检索索引 | PG `agent_api_vectorindex` + DocumentChunk/EmbeddingRecord/代际与 embedding 身份列；SQLite 为库内 EmbeddingRecord | 代际切换由入库事务控制；任务 outbox 也在数据库 | **整库**恢复，不能仅恢复向量表；恢复后验证 active generation、模型/算法/index version 及检索结果 |

`audit_media_references` 只读检查数据库引用和受管前缀 `blog/`、`knowledge/`、私有图片目录的缺失/孤儿数量；不会列出私有正文或删除对象。它覆盖可解析的 `/media/blog/<uuid>.<ext>` 引用，不能证明任意外链、旧式非规范对象键或 Bucket 隐藏版本都完整。出现差异时先保留现场，按备份和业务记录调查，不能直接批量删。当前未配置定期备份、自动过期或自动清理；不能把代码中的清理函数当作已运行的保留策略。

## 目标与备份操作

**拟定服务目标**：RPO ≤24 小时，RTO ≤4 小时；每日一次完整备份，成功校验后保留最近 30 份，并至少每月做一次隔离恢复。它们是待部署的目标，**当前没有证据证明达到**。若业务要求更低 RPO，须加入经验证的 WAL/PITR 与对象版本化；单次日备份最多可能丢失一天数据。备份加密、最小权限、异地副本和生命周期规则须在实际平台落实。

1. 记录应用 commit/镜像、Django 迁移表、PG/pgvector 版本、embedding 配置身份、UTC 起止时间和文件存储后端。备份内容含私人资料，限制操作人和保存位置，不在日志输出正文/密钥。
2. 暂停所有写入口及 worker/beat，等待在途上传、入库和审批事务结束；记录静止窗口。仅暂停 HTTP 写入而放任 worker 写入无法保证 DB 与文件同步。公共文件卷、私有卷和 Bucket 在整个快照窗口内都必须保持静止。若平台无法做到，需先实现可验证的对象版本/提交水位方案，不应声称此流程为一致备份。
3. 在隔离备份目录使用受保护连接信息运行 `pg_dump --format=custom --file=database.dump "$DATABASE_URL"`，并校验命令退出码。复制 `media_data`、`private_note_data`；若 `BLOG_MEDIA_STORAGE=s3`，还要按对象版本复制 Bucket 的 `blog/` 对象，不能只复制公开卷。生成每个文件/对象的 SHA-256 清单和对象版本 ID；清单与数据库 dump 属同一备份批次。验证份数、大小、哈希和可读性后再恢复写入。不得用 `docker compose down -v` 作为备份或清理手段。
4. 私有源文件及公开/私有图片不能从数据库重建；Broker/Redis 不作为权威持久副本，但恢复后须重新启动 outbox 分发并检查遗留任务。若备份期间发生任何写入，整批标记不一致并重做。

## 隔离恢复与检查

1. 创建**新** PostgreSQL 数据库、新文件卷和独立 Bucket/前缀；绝不指向现有生产/开发数据库或用户文件。部署同一镜像、配置和 pgvector 扩展版本。先校验清单，再运行 `pg_restore --exit-on-error --single-transaction --no-owner --no-privileges --dbname="$ISOLATED_DATABASE_URL" database.dump`，恢复两份文件卷及 Bucket 对象。不要在恢复过程中运行迁移或重建索引；先按快照版本读回，之后再单独评估升级。
2. 以隔离凭据启动应用，确认迁移版本、文档 active generation/索引身份和任务状态；运行 `python manage.py audit_media_references`。缺失引用为恢复失败；孤儿先调查是否来自历史删除/未绑定上传，默认不清理。
3. 抽验已发布文章正文和图片、私有附件文件字节及匿名/他用户/他 workspace 的 401/404、本人 200；按原 workspace 检索已知文档并确认其他 workspace 无命中。记录开始/结束 UTC、实际 RTO、备份时间到故障点的实际 RPO、错误及处置。
4. 对逾期 outbox/运行状态按 I-008/I-006 的恢复规则处理。仅在隔离验收成功后再制定业务切换方案；本文没有授权生产恢复。

## 本机可重复演练与结果

运行 `.venv\Scripts\python.exe backend\scripts\rehearse_backup_restore.py`。脚本强制 `settings_e2e`、本地 SQLite/哈希 embedding、独立临时数据库和三个临时目录，禁用 `.env` 加载和远程追踪；生成演练数据、用 SQLite backup API 复制数据库、复制媒体、写 SHA-256 清单，恢复到第二套临时根后在新进程验证，再自动删除临时根。它**不读取现有用户数据**，不能替代 PostgreSQL/pgvector/Bucket 演练。

2026-10-23 本机演练（Windows、根 `.venv`）：最终四类对象演练的备份 0.024 秒；恢复、校验哈希及应用验证 3.278 秒；含造数/迁移总计 9.043 秒。4 个文件（DB、文档源、公开图、私有附件）哈希一致；文章及两类图片字节、匿名 401/同 workspace 跨用户 404/同用户跨 workspace 404/本人 200、文档源及本地哈希检索、跨空间零命中、孤儿/缺失均为 0。第一次演练虽然业务检查通过，但因 SQLite 连接未关闭导致 Windows 临时目录清理失败；修复后最终进程退出码 0、临时根已删除。上述秒数仅为很小的隔离 SQLite 样本，**不是**生产 RTO/RPO 证明。

仍待验证：真实 PostgreSQL/pgvector + broker/worker、文件卷及 S3 Bucket 同批备份和隔离恢复；全量大小/并发下的 RTO/RPO、Bucket 对象版本、跨版本兼容、备份加密/权限/异地保留和恢复后可写入；缺少这些证据，I-011 保持未关单。
