# I-022：草稿生成、人工审批与图恢复评估

日期：2026-10-24。结论：**延期跨请求 LangGraph 图及 checkpoint**；本轮只修复核查时确认的现有发布审批失效边界。延期不表示已具备图状态恢复。

## 当前可用的用户路径

| 步骤 | 已实现 | 边界 |
| --- | --- | --- |
| 从资料提问 | `/api/agent/chat/stream/` 返回正文、当轮来源和 `run_id`；会话/`AgentRun` 入库，断线可查结果。前端显示引用，并有“去写博客”入口。 | 入口打开写作台，作者仍需核对/复制需要的内容；没有自动生成“带来源的文章草稿”并把来源绑定到文章。`AgentRun` 不是图 checkpoint。 |
| 辅助写作 | 登录作者可调用 `/api/agent/blog/writing-agent/generate/` 获取 Markdown 建议；`note_summary` 仅可汇总本人、当前 workspace 的私有笔记，并在响应中标注笔记来源。作者选择追加/替换。 | 一般 `draft` 模式以请求传入草稿/指令为输入，没有可验证的检索引用链。未提交的编辑器草稿按用户/workspace 保存在浏览器本地，不能当作服务端跨设备流程状态。 |
| 提交与人工发布 | `/api/agent/blog/articles/` 保存 `BlogArticle(draft)` 和 `ApprovalRequest(pending)`；管理员按当前角色/workspace 审批。已发布文章修改形成待审 `BlogArticleRevision`，原公开版保持不变，审批核对 `base_version`。 | 这是持久业务记录与人工审批，可在进程重启后继续处理待审单；没有“恢复到图的某个节点”。发布到知识库的入库另有后台状态，公开完成不等于索引完成。 |

当前 [I-015 开发者路径](I-015-核心路径页面地图与流程原型.md)只验证了 mock 引用后的手动写作入口，真实用户完成率、真实资料到文章的来源依据性和跨设备中断诉求都未取得。现有业务能满足“作者看引用→编辑→提交→管理员批准”的人工流程；**尚无经过产品确认、必须暂停并重启后继续同一图运行的场景**。因此不为框架增加自动发布、图节点或持久 saver。

## 本轮确认并修复的现有审批缺口

核查发现：未发布文章的操作者 `PATCH` 可以修改正文等字段，旧待审发布单仍是 `pending`；旧审批 payload 原来只存文章 ID/标题，批准时读取文章当前正文。隔离回归先复现“审批创建后改正文，旧审批仍可执行”。这与当前人工发布语义冲突，故做小范围修复：

- 新发布审批记录写入文章标题、摘要、封面、正文、分类、标签、状态和公开版本的 SHA-256 指纹；批准非修订文章前重新计算。指纹仅用于一致性，审批仍必须通过服务端管理员和 workspace 校验。
- `PATCH` 改动文章/发布相关字段时，在同一数据库事务使该文章的待审发布单失效；提交新的发布单后才能批准。已发布修订仍用独立 `BlogArticleRevision` 快照和 `base_version` 校验。
- 对本轮修改前已存在、没有指纹的待审发布单，审批前保守检查文章 `updated_at` 是否晚于审批创建时间；若晚于则失败并要求重新提交。该兼容路径不能侦测绕开模型时间戳的外部数据库写入，运维应让历史待审单重新提交后再批准。
- 同一新内容产生两张待审发布单时，先批准的事务会更新公开版本；后一张的指纹不再匹配，不能再次执行发布。已执行单重复决策返回冲突。

作者修改待审文章应重新提交发布请求；审批页出现 `failed` 或旧请求被拒绝时，先核对当前内容并发起新审批。代码位置：`views/blog_articles.py`、`views/common.py`、`services/blog.py`。没有迁移、没有改变文章和审批表结构，也没有自动发布真实内容。

## 是否引入持久图的判断条件

先由产品/真实用户任务明确：需要自动把**哪些**资料来源变成草稿；作者能修改哪些字段；谁批准内容与谁最终发布；多次修改是否重新走审批；离线/跨设备或进程重启后要从**哪一个具体步骤**继续。若普通 `BlogArticle` 草稿 + `ApprovalRequest` 已满足，继续复用业务状态，不引入图恢复。

若将来证明确需暂停图执行，再设计 `workflow_run_id` 与草稿 ID、审批 ID、内容版本、来源快照的关联；恢复时重查用户、workspace、角色、来源可见性和审批版本；外部发布副作用使用持久幂等键；覆盖拒绝、权限撤销、修改后重审、并发/重复恢复和进程强杀。必须在隔离 PostgreSQL 与实际 worker/部署拓扑验证，不能由 `AgentRun` 或浏览器草稿推断图恢复能力。

当前锁定 `langgraph==0.2.76`、`langchain-core==0.3.86`、`langchain-openai==0.2.14`；本机 `.venv` 另安装 `langgraph-checkpoint==2.1.2` 基础接口包。`backend/agent/simple_agent.py` 仍直接 `workflow.compile()`，没有配置持久 saver、`thread_id` 或中断恢复 API。本轮没有升级依赖，也没有声称任何数据库 saver 与当前版本兼容。将来选型须单独做版本矩阵和进程重启演练；[I-007 决策](I-007-LangGraph工作流决策.md)继续有效。

## 验证与剩余风险

- 本轮新增审批回归先失败 2 项，确认旧审批失效与内容绑定缺口；修复后的测试结果和命令以[跟踪表实施记录](AI全栈与Agent工程改进跟踪表V1.0.md#每项任务的实施记录)为准。
- 隔离 Django 测试只验证本地 SQLite、mock/本地哈希和 API 状态；不等于真实模型带来源草稿质量、真实 PostgreSQL 并发、进程重启图恢复或生产审批演练。
- 指纹只约束发布时所审的业务字段；历史无指纹审批的时间戳兼容逻辑有上述边界。若要对历史待审单提供严格保障，需要单独制定批量作废/重提流程并在隔离数据副本演练。

本项保留“延期、待场景确认”状态；当上述场景、数据来源、审批人与恢复点明确后再决定是否启动完整 I-022。当前修复只保护已有人工发布流程。
