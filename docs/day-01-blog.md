# 为什么企业级 Agent 不能只是一个 ChatBot：LangChain、LangGraph、RAG 与 MCP 的关系

很多人第一次接触 Agent 应用时，会自然地把它理解成一个更聪明的 ChatBot：用户提问，模型回答，最多再接几个工具调用。这个理解并不算错，但它只覆盖了 Agent 工程的入口层。真正的企业级 Agent 系统，需要解决的是知识、流程、权限、观测、协作和长期演进的问题。

## ChatBot 是交互形式，不是系统边界

ChatBot 解决的是“人如何和系统对话”。企业真正关心的是：系统能否基于内部资料回答问题，能否在复杂流程中做出可追踪的决策，能否在关键节点交给人审批，能否把工具调用、检索结果、失败原因和成本都记录下来。

如果只做一个聊天框，系统很快会遇到几个问题：

- 知识来源不可控，回答无法引用企业资料
- 多步骤任务缺少状态管理，中途失败难以恢复
- 工具调用没有权限边界，安全风险很高
- 结果不可评估，无法持续优化
- 业务流程需要人工审批时，模型无法自然停下来等待人类决策

所以企业级 Agent 不是“聊天页面 + 大模型 API”，而是一套围绕知识、工具、流程和治理构建的软件系统。

## LangChain 负责快速连接能力

LangChain 更像 Agent 应用的工具箱。它提供模型调用、Prompt、工具封装、文档加载、文本切分、Embedding、Retriever 等基础能力。对于快速构建原型、连接不同模型和检索组件，LangChain 非常合适。

在企业知识智能体中，LangChain 可以负责：

- 加载 PDF、Word、Markdown、网页等文档
- 对文档进行切分和向量化
- 调用 Embedding 模型
- 封装搜索、数据库、GitHub 等工具
- 组合基础的 RAG 问答链路

它让我们不必从零实现每个基础组件。

## LangGraph 负责可控的 Agent 工作流

当任务从一次问答变成多步骤协作时，只靠链式调用就不够了。企业流程通常需要状态、分支、循环、重试、人工审批和恢复能力。LangGraph 的价值就在这里。

LangGraph 可以把 Agent 运行过程建模成状态图：

- 节点表示模型推理、工具调用、检索、审批、总结等步骤
- 边表示流程转移
- 条件边决定下一步走向
- 状态保存上下文、工具结果、审批信息和中间产物

这使得 Agent 不再是一次性脚本，而是可恢复、可观测、可控制的长期运行流程。

## RAG 让 Agent 使用企业知识

RAG 的核心是让模型回答时基于可检索的外部知识，而不是只依赖模型参数里的通用记忆。企业场景中，知识通常来自内部制度、产品文档、项目资料、会议纪要、代码仓库和客户案例。

一个完整 RAG 链路通常包括：

- 文档上传
- 文本解析
- 文档切分
- 向量化
- 存入向量数据库
- 查询检索
- 重排
- 带引用回答

在本项目里，PostgreSQL + pgvector 会同时承载业务数据和向量数据。这样可以减少系统复杂度，并方便把用户、文章、文档、权限和检索结果放在同一个数据治理边界内。

## MCP 让工具接入变得标准化

企业 Agent 不可能只回答知识库问题，它还需要访问外部工具：搜索、文件系统、GitHub、数据库、内部 API、工单系统等。MCP 的意义是为工具接入提供统一协议，让 Agent 能以更标准的方式发现和调用工具。

相比在代码里为每个工具写一套临时适配，MCP 更适合长期维护：

- 工具边界更清晰
- 接入方式更统一
- 权限和审计更容易落地
- Agent 可以面向协议而不是具体工具实现编排

## 四者之间的关系

可以这样理解：

- LangChain 提供组件和连接器
- LangGraph 编排长期、有状态、可恢复的 Agent 流程
- RAG 提供企业知识检索与引用能力
- MCP 提供外部工具的标准化接入方式

它们不是互相替代的关系，而是分工协作。LangChain 帮我们更快搭建能力，LangGraph 帮我们把能力组织成可靠流程，RAG 让回答贴近企业知识，MCP 让 Agent 可以安全、标准地使用外部工具。

## 本项目的第一天

第一天先不急着实现复杂智能体，而是搭建工程底座：Vue 3 前端、Django 后端、PostgreSQL、Redis、Docker Compose、文档目录和 Agent 目录。这个底座决定了后续能力能否被稳定地接入、测试和部署。

企业级 Agent 的难点不只在模型，而在工程。一个真正能落地的 Agent 系统，必须从第一天就把知识管理、权限、观测、异步任务、部署和评估放进架构视野里。
