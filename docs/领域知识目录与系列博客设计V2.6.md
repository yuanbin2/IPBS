# 领域知识目录与系列博客设计 V2.6

> 状态：B-042A/B/C 已于 2026-10-03 本地实现并测试（见第 9 节实现记录）；性能与用户任务验收待外部环境。参考的是[博客园“AcWing 算法基础课题解目录”](https://www.cnblogs.com/littlehb/p/15393332.html)的**组织方式**：课程分成多讲，讲内按知识点分组，每个知识点链接到多篇博客。本文不导入该页面的文章、题解或目录文字。力扣导入 B-041 可生成单篇文章；B-042 再把已发布文章编排成学习路径。

## 1. 目标与层级

用户能创建一个领域主页，在领域里放多门课程或专题；每门课程分章节，每章分知识点，知识点下排列若干篇现有博客。一个领域可有多个课程，一篇文章也可放进不同领域，但在同一个领域中只出现一次。例子只说明结构：

```text
算法（领域）
├─ 基础课（课程/专题）
│  ├─ 第一讲 基础算法（章节）
│  │  ├─ 排序（知识点）
│  │  │  ├─ 快速排序：我的实现（本站文章）
│  │  │  └─ 归并排序的边界处理（本站文章）
│  │  └─ 二分（知识点）
│  └─ 第二讲 数据结构（章节）
└─ 进阶专题（课程/专题）
```

领域、课程、章节、知识点都由作者命名，不把“基础课”或“第一讲”写死在代码中。根领域加最多三级目录节点；文章可直接放在领域根或任何目录节点下，避免用户为了只有一篇文章而被迫创建空层。超过深度时提示拆成另一个领域。目录显示的是**文章引用**，不复制文章正文；分类、标签和时间归档继续各司其职。

读者的主要任务是：从领域列表找到想学的方向；在目录中折叠/展开、搜索、跳到章节、按顺序读文章；看完一篇文章能回到所属目录或前后篇。作者的主要任务是：建目录、加文章、排序、预览、提交公开审核、以后逐步补全。目录的标题、说明和顺序是编辑内容，不应未经审核直接改变公开版。

## 2. 为什么使用独立的“领域目录”模型

| 方案 | 判断 |
| --- | --- |
| 把目录写成一篇 Markdown 文章 | 简单，但手工维护链接、顺序、权限和文章删除状态；不能稳定生成前后篇和准确计数。可作为旧数据迁移来源，不作为系统真相。 |
| 把现有 `ArticleCategory` 改为多级分类 | 现有分类名/slug 全局唯一、一篇文章只有一个分类，主要用于筛选。强行改树会影响现有分类过滤、标签、相关内容和旧数据；同一文章跨多个学习路径也做不到。 |
| 新建领域根＋目录节点＋文章关系 | 领域提供独立的学习顺序、介绍和审核；节点用邻接表 `parent_id` 表示有限深度树，文章关系用显式排序字段。可以保留现有分类/标签，不迁移或复制正文。选此方案。 |
| 嵌套集合/物化路径 | 适合很深或海量树；本功能限制为根＋三级节点，按根一次取回少量节点组树即可。移动目录时邻接表更直接，迁移与并发边界也更易审计。 |

领域目录是博客组织层，不是 RAG 的 `KnowledgeBase`，目录发布也不自动把草稿文章加入知识库。

## 3. 页面与交互

### 公开读者

- 博客首页增加“领域目录”入口，列出**已审核公开**的领域卡片：标题、说明、可见文章数、更新时间；可按标题查找。页面地址建议 `/blog/collections/:publicId`，使用不可变 UUID，不让重命名断链。
- 目录页左侧是独立滚动且可折叠的树，右侧为领域介绍、当前节点说明与文章清单；窄屏改为顶部可收起目录。面包屑显示“领域 / 课程 / 章节 / 知识点”。点击节点滚到正文对应区域，左侧树不随正文一同滚走。URL 以 `?node=<id>` 保留当前位置，刷新/分享可恢复。
- 每个节点展示当前可见文章数，阅读顺序按显式 `position`，同序再按稳定 ID；文章卡保留真实作者、原标题、摘要、发布状态，不允许目录编辑者伪造作者。文章详情页带目录上下文时提供“返回目录、上一篇、下一篇”；若一篇文章属于多个领域，当前链接只选择一个上下文。无效上下文不影响正常阅读。
- 公开目录从已审批的目录快照生成，并在每次读取时只解析**当前仍为 published、且与目录同 workspace**的文章。草稿、拒绝、归档、删除文章及其计数都不泄露。空章节可显示“待补充”但不能露出未发布文章标题。

### 作者管理

- 登录用户可创建自己的**私有领域草稿**，填写标题、简介，添加/重命名/移动/删除课程、章节、知识点节点；从本站已发布文章搜索选择加入，不复制正文。前端初始可以用“上移/下移”按钮和键盘操作，拖拽可后置，避免只靠鼠标排序。添加失败说明原因，不丢原顺序。
- 目录草稿可预览最终排版；提交后进入现有管理员审核队列。已经公开的领域继续显示旧快照，作者可以修改私有工作版，再提交新快照；审核通过才替换公开版。拒绝时保留草稿与意见，作者可修改重提。管理员可在同 workspace 审核，重复/过时审批不得覆盖新版。
- 首期目录只关联**已发布**文章。需要先规划未写完的内容时，作者可建立空目录节点并在私有预览看到“待补充”；私有草稿文章的成员关系留到稳定作者身份字段建立后再考虑。现有 `BlogArticle.author_name` 是字符串，匿名投稿可填同名昵称，不可拿它当未公开文章的所有权凭据。
- 作者可以收录同 workspace 其他作者的公开文章，作为带真实作者署名的阅读清单；不得因此获得修改原文权限。若产品最终只希望“我的文章”，可在选择器默认筛选自己的已发布文章，但服务端权限判断不能依赖 `author_name` 字符串。

## 4. 数据模型与约束

建议新增三个表，不改 `ArticleCategory`、`ArticleTag`、`BlogArticle.content`：

| 表 | 主要字段 | 关键约束 |
| --- | --- | --- |
| `BlogCollection` | `id`、`public_id` UUID、`owner` FK User、`workspace_key`、`title`、`slug`、`description`、`draft_version`、`publication_version`、`published_snapshot` JSON、`pending_snapshot` JSON、`pending_approval` FK nullable、时间戳、可归档标记 | `public_id` 唯一；`(workspace_key, owner, slug)` 唯一；标题/简介限长；所有写操作须同 workspace 且为 owner，审核例外。只有非空 `published_snapshot` 才可能公开。 |
| `BlogCollectionNode` | `id`、`collection` FK、`parent` self FK nullable、`title`、`description`、`position`、时间戳 | 父节点必须属于同一 collection；无环；根下最多三级节点；节点总数上限 100；同级名称可重复但排序稳定。删除/移动只作用私有工作版。 |
| `BlogCollectionEntry` | `id`、`collection` FK、`node` FK nullable（空表示领域根）、`article` FK、`position`、时间戳 | 非空 node 必须属于同一 collection；article 必须同 workspace 且为 published；`(collection, article)` 唯一，领域之间可重复收录；每领域最多 500 篇。文章删除时关系可级联，但公开快照仍须在读取时过滤失效 ID。 |

公开快照只存目录的受限纯文本标题/说明、节点顺序和文章 ID/顺序，不存文章正文、私有笔记、模型结果、任意 HTML 或未经审核的实时目录。提交时在事务内对草稿树生成不可变 `pending_snapshot` 与哈希，创建 `ApprovalRequest.Action.PUBLISH_BLOG_COLLECTION`，payload 仅引用 collection ID、版本和快照哈希。管理员审批用 `select_for_update` 验证 workspace、pending approval ID、版本与哈希，然后将该快照原子设为 `published_snapshot`；拒绝则保留现有公开快照和私有草稿。新提交使旧待审请求失效。作者可在待审期间继续编辑工作版，但待审快照不随之变化。

目录和文章的公开可见性分开判断：即使快照批准，若某文章后来归档/删除/跨空间异常，公开读取仍立即隐藏它。计数、搜索、前后篇都从**过滤后的**公开条目计算。避免为每个卡片单独查库：一次取快照中所有 article ID，再用同 workspace 的 published queryset 批量取文章和所需 tags/category，按快照顺序组装。规模上限给出可控响应大小；性能目标在真 PostgreSQL 上单独验证。

旧数据迁移只建空表，绝不按分类自动重排旧文章或改已有 slug。现有手写 Markdown 目录可在后续提供“从本站链接生成预览”的**人工确认迁移**，只接受本站可见文章链接，不抓取参考博客页面、不复制其文章。

## 5. API 契约建议

| 方法与路径 | 身份 | 功能 |
| --- | --- | --- |
| `GET /api/agent/blog/collections/` | 公开 | 分页列出已批准目录的摘要与可见文章数，支持限长 `q`。 |
| `GET /api/agent/blog/collections/<uuid>/` | 公开 | 返回已批准快照的树与同 workspace 当前 published 的文章摘要。不存在/未公开统一 404。 |
| `GET /api/agent/blog/collections/mine/` | 登录 | 仅列本人 workspace 的草稿、待审、公开版本状态。 |
| `POST /api/agent/blog/collections/` | 登录 | 创建私有根目录。 |
| `GET/PATCH/DELETE /api/agent/blog/collections/<uuid>/draft/` | owner | 私有工作版，乐观版本号防多标签覆盖；公开过的目录删除改为归档申请。 |
| `POST/PATCH/DELETE /api/agent/blog/collections/<uuid>/nodes/...` | owner | 节点增改移动/删除，服务端检查同树、深度、环、版本。 |
| `POST/DELETE /api/agent/blog/collections/<uuid>/entries/...` | owner | 选择/移除已发布文章；同空间、去重、限额。 |
| `POST /api/agent/blog/collections/<uuid>/reorder/` | owner | 一次提交单个父节点下完整节点/文章顺序，事务内验证全集、无重复与版本；失败不部分写。 |
| `POST /api/agent/blog/collections/<uuid>/submit/` | owner | 冻结待审快照，返回待审 ID；重复同版本请求幂等。 |

审批仍用既有管理员审批入口，但需新增该 action 的执行分支和前端可理解的摘要/预览。所有写接口使用真实 JWT、`workspace_key` 和 owner FK，不能信客户端传入的 owner/workspace/status；公开只读接口不能回传私有草稿或 pending snapshot。PATCH/重排要求 `expected_version`，不匹配返回 409。错误码/请求体限额沿用项目风格。API 命名可按现有路由微调，但语义与权限不可删减。

## 6. 安全、失败与回滚

- 目录标题、说明、节点标题是纯文本，限制长度和字符，前端以 Vue 文本插值呈现，禁止不受控 `v-html`。文章正文继续走现有 Markdown→安全 HTML 渲染；目录不新增外站抓取、文件上传或 AI 生成。
- 目录移动检查祖先链/环及深度，在 `transaction.atomic` 中锁相关行；重排必须验证提交的 ID 集合恰好等于当前可排序集合。并发编辑返回 409 和刷新提示，不悄悄覆盖。
- 创建/删除/重排限制节点数、文章数、请求体大小和操作频率；公开读取分页/缓存并正确失效，避免每个节点 N+1 查询。不要从快照泄露草稿文章 ID、标题或隐藏节点内容。
- 迁移前备份；先运行 schema/权限/历史数据测试。独立新路由和导航入口可关闭。若回滚前端，新目录表不影响旧文章/分类；若回滚后端迁移，须先确认没有作者创建的目录数据，不能直接删表。真实 PostgreSQL、Railway 多实例/缓存及浏览器移动端另做发布验收。

## 8. 本轮选择

按 B-042A→B→C 的顺序推进。第一版允许自由命名、有限深度、多文章、多课程、多领域、跨领域复用同一篇已发布文章。可视化目录编辑优先做可靠的按钮排序；拖拽、学习进度、先修依赖、AI 自动编排、外部链接和从参考网页批量导入都不是首轮条件。这样既保留参考目录的可读层次，又让作者实际管理自己的文章而无需手改一大篇链接表。

## 9. B-042A/B/C 实现记录（2026-10-03）

### 9.1 落地范围与关键设计理由

**数据层（B-042A）**：迁移 `backend/apps/agent_api/migrations/0040_blog_collections.py` 建三表，全部集中在 `models/blog.py` 末尾，不改 `ArticleCategory`/`ArticleTag`/`BlogArticle` 语义：

- `BlogCollection`：`public_id` UUID 作公开标识（重命名不断链），`owner` FK + `workspace_key` 双约束（`(workspace_key, owner, slug)` 唯一），`draft_version` 为私有工作版乐观锁，`publication_version` 为公开版代数，`published_snapshot`/`pending_snapshot`/`pending_approval` 支撑三态分离，`archived_at` 让已公开领域只能归档不能真删。
- `BlogCollectionNode`：同树 `parent` 邻接表（self FK），`position` 显式排序；删除/移动只作用于工作版。
- `BlogCollectionEntry`：`node` 可空表示直接挂领域根；`(collection, article)` 唯一保证领域内不重复、跨领域可复用；`article` 只接受同 workspace 且 `published` 的文章。

**约束实现**：根下最多三级、单领域 100 节点/500 篇文章、同树/无环/深度在 `services/blog_collections.py` 的纯函数中校验，移动前沿祖先链判环、按子树高度合并计算最终深度；所有写接口包在 `transaction.atomic` + `select_for_update` 内，`expected_version` 不匹配一律 409，失败不部分写。

**权限**：写接口（创建/draft/节点/文章/排序/提交）全部走 `jwt_user_from_request` 解析真实 JWT，再用 `get_or_create_profile` 取 workspace，按 owner+workspace 过滤全部查询；绝不信任请求体里的 owner/workspace/status，也不把管理员的审批权限当成可编辑任意私有目录的凭据。

**审核（B-042B）**：提交时对草稿树生成**纯文本**快照（标题/说明/节点顺序/文章 ID 与顺序，不含正文、笔记、HTML）并计算 SHA-256；`ApprovalRequest` 新增 `PUBLISH_BLOG_COLLECTION` action，payload 只放 collection ID、submit_version 与快照哈希。批准分支在 `execute_approval_request` 中锁行校验 workspace、pending approval ID、版本与哈希后原子替换 `published_snapshot` 并递增公开版；重提交会先把旧 pending 标记 REJECTED（过时审批再批会 400）；拒绝走 reject 分支清空 pending 快照、保留公开旧版与私有草稿。

**公开读取**：`/blog/collections/`（分页+限长 q）、`/blog/collections/<uuid>/`、`/blog/collections/context/?article=<id>&collection=<uuid>`（返回目录、节点路径与前后篇；一篇文章属多个领域时优先用读者来源的 collection）。三者都只读已批准快照，并每次用**单条**同 workspace published queryset 解析全部文章 ID（测试断言详情读取 SQL 条数有上限），下架/删除的文章立刻从树、计数、搜索与前后篇消失；未公开目录对非 owner 统一 404，公开接口不回传 pending/draft 内容。

**前端（B-042C）**：新增 `CollectionsView.vue`（公开列表）、`CollectionDetailView.vue`（阅读页：左侧独立滚动可折叠树、面包屑、节点文章清单、目录内搜索、`?node=` URL 刷新恢复、≤900px 折叠为顶部目录）、`CollectionManagerView.vue`（“我的领域”：创建/重命名/上下移排序/删除节点、加入与移除已发布文章、提交状态与被拒原因），均用 Vue 文本插值渲染目录文本，无 `v-html`。`BlogView.vue` 顶部加“领域目录”入口，文章详情新增 `collection-context` 上下文条（返回目录/上一篇/下一篇），不触碰只读、原位编辑、评论与笔记逻辑。新增三条静态段路由 `/blog/collections`、`/blog/collections/mine`、`/blog/collections/:publicId`，先于 `/blog/:slug?` 注册，不影响原有文章路由。
