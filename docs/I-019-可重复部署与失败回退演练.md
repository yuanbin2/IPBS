## 发布门禁与失败处理

1. CI 的单测、类型检查、构建、PostgreSQL 集成和 E2E 必须对应同一候选源码；I-018 的 GitHub 实际运行仍需核实。用唯一发布 ID 构建并保存后端/前端镜像 ID 或 digest。禁止从漂移的 `local`/`latest` 标签推断版本。
2. 按 [I-011](I-011-数据生命周期与备份恢复.md)对数据库、公开/私有文件及向量索引作同批备份，恢复到隔离环境。用候选镜像在副本上执行 `manage.py migrate --plan`、实际迁移和核心接口/数据检查；失败即停止发布并保留日志。`--plan` 不能证明迁移真的会成功。
3. 逐项审查旧应用与新 schema 的兼容性。只有验证过的扩展式迁移可在旧应用仍有写入时执行；删除/改名/改类型、数据回填或向量结构调整须维护窗口，停止写入和 worker。正式目标先显式迁移和 `collectstatic`，迁移命令退出 0 且 `migrate --check`/`/api/ready/` 通过后再启动新后端、worker、前端。Compose 后端和镜像入口默认不自动迁移或收集静态文件，预检不会写共享静态卷。
4. `/api/health/` 只检查应用进程；`/api/ready/` 检查数据库连接与未应用迁移，Compose 后端健康检查使用后者。还需实测登录、文章、私有附件权限、检索、异步入库/队列以及 SPA 资源。就绪接口目前不检查 Redis、RabbitMQ 或 worker，不能独自作为完整验收。
5. **数据库未变更时**：候选失败则停止候选，改回旧 `BLOG_RELEASE_ID`，以 `docker compose up -d --no-build` 启动保留的旧镜像，并重复就绪与核心数据检查。**数据库已变更时**：仅在预先验证旧应用与新 schema 兼容时回退应用；否则保持维护窗口，从同批备份恢复数据库、向量、媒体到隔离目标，验收后制定切换。不要假定执行反向迁移就能恢复数据。

当前迁移实例说明回退风险：`0020_create_pgvector_index` 的反向操作会删向量表；`0031_embedding_space_identity` 会隔离旧 embedding、为 PG 向量表加身份列，反向为 `noop`；`0033`/`0035` 等回填反向也是 `noop`。因此“Django 报告可反向运行”不等于原始数据可恢复。应用回退只是换回旧代码/镜像；数据恢复必须使用 I-011 的一致备份。当前最新 `agent_api` 迁移为 `0049_request_task_telemetry`（本轮观测）。

## 本机隔离演练

命令：`.venv\Scripts\python.exe backend\scripts\rehearse_deploy_rollback.py`。脚本只在系统临时目录建立源码快照、构建产物及 SQLite 数据，不读取 `backend/db.sqlite3`、用户媒体或真实 `.env`，退出时销毁临时目录。A 版先迁移并造一篇已发布文章、一张私有附件及一份已索引文档，启动真实 Django HTTP 进程；B 版在**临时快照**加入故意失败的 `0050_i019_injected_failure` 迁移。先在数据库副本运行 B 迁移并要求非零退出，再用 B 启动 HTTP 进程观察 `health=200`、`ready=503`，最后停止 B、重新启动 A 并复验同一数据根。

2026-10-24 最终运行退出码 0：A 首次部署及接口检查 3.322 秒；B 的迁移副本明确失败，运行数据的 79 条迁移记录未变；B 存活但未就绪；回退 A 及复验 3.190 秒。回退前后 `/api/health/`、`/api/ready/`、SPA 入口及 JS 资源、已发布文章、登录、私有图片匿名 401/本人 200、知识检索均通过。首次脚本运行有 Windows GBK 子进程解码噪声；明确使用 UTF-8 后重跑无该异常。
